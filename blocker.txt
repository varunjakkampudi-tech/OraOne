ITEM 1 - EMAIL DELIVERY (SMTP) FOR SIGN-IN CODES      [old item 1, 26]
=====================================================================
Why: sign-in works only if the 6-digit code is emailed. Without SMTP, users cannot sign in.
Status: the code now fails closed (users see an error instead of a fake success), but no email
leaves the server until this is set up.

Step 1. In the Hostinger control panel, open Emails and create a mailbox:
        Address: noreply@oraone.in
        Choose a strong password and save it in your password manager.
Step 2. In the Hostinger email settings, find the outgoing (SMTP) server name, port and SSL setting.
        Copy them from the Hostinger page. Do not guess them.
Step 3. On the server, edit /opt/oraone/backend/.env and add these lines (replace each <FILL> value):

        SMTP_HOST=<FILL: outgoing server name from Hostinger>
        SMTP_PORT=<FILL: port from Hostinger>
        SMTP_USER=noreply@oraone.in
        SMTP_PASSWORD=<FILL: mailbox password - secret, server file only>
        SMTP_FROM=noreply@oraone.in
        SMTP_USE_SSL=<FILL: true or false, as Hostinger specifies for that port>

Step 4. Restart the services (see "How to use" above).
Step 5. Test: open https://oraone.in/auth/sign-in, enter your own email, and ask for a code.
        The code should arrive within a minute. If it does not, check the spam folder, then run:
            docker logs oraone-prod-backend --tail 200 | grep -i smtp
        Look for "email sent via SMTP". Do not paste log lines that contain a password.

Tell me: "SMTP done" and the sender address you used (non-secret).

ITEM 2 - WHATSAPP (META CLOUD API)                    [old item 2]
=====================================================================
Why: WhatsApp messages reach the assistant only after Meta is connected.

Step 1. Go to https://developers.facebook.com, open your app, then WhatsApp > API Setup.
Step 2. Add your business phone number. Meta sends a verification code by SMS or voice.
        You must receive that code yourself. Complete the steps Meta shows.
Step 3. Add a payment method for business-initiated messages (your choice, your account).
Step 4. Create a permanent access token for a system user (Business Settings > System users).
        Give it the WhatsApp permissions for your app.
Step 5. Note the App Secret: App settings > Basic > App secret (click Show).
Step 6. Choose a verify token: any random text of at least 20 characters. Keep it secret.
Step 7. On the server, edit /opt/oraone/backend/.env:

        META_WHATSAPP_ACCESS_TOKEN=<FILL: permanent system user token - secret>
        META_WHATSAPP_APP_SECRET=<FILL: App secret - secret>
        META_WHATSAPP_VERIFY_TOKEN=<FILL: the verify token you chose - secret>

Step 8. Restart the services.
Step 9. In Meta > WhatsApp > Configuration > Webhooks:
        Callback URL:  https://oraone.in/api/channels/meta/inbound
        Verify token:  the same value as META_WHATSAPP_VERIFY_TOKEN
        Click Verify and save. Then subscribe to the "messages" field.
Step 10. In OraOne Studio > Channels > WhatsApp, enter the Phone number ID and WhatsApp Business
         Account ID shown in Meta. These are not secrets; they go in Studio, not in .env.
Step 11. Test: send a WhatsApp message to your business number from another phone.
         The conversation should appear in Studio > Inbox within a minute.

Tell me: "WhatsApp done" and the phone number (non-secret, for example +91...).

ITEM 11 - ENCRYPTED OFF-HOST BACKUPS AND A RESTORE DRILL   [old item 15, 24, 44]
=====================================================================
Why: if the server is lost, the data must be restorable from somewhere else.
What the repository has today:
  - backend/scripts/weekly_backup.py writes an encrypted file on the server. It does NOT copy the
    file off the server, and it does not delete old files.
  - backend/scripts/backup_restore_drill.py exists. It has not been run against a real backup.
  - docs/operations/BACKUP-RESTORE.md has the rehearsal of migration rollback on a scratch database.
    That is not a production backup.

Step 1. Choose an off-host destination you control: another cloud storage account, or another
        server. Note the cost and the retention period (for example 30 days).
Step 2. On the server, create a passphrase file that only root can read:
            install -m 600 /dev/null /root/oraone-backup-passphrase
            nano /root/oraone-backup-passphrase
        Type a long passphrase and save. Store the same passphrase in your password manager.
        Without it, the backups cannot be restored.
Step 3. Create the backup folder:
            mkdir -p /var/backups/oraone
Step 4. Give the backup job these settings (in /opt/oraone/backend/.env, or in the environment the job
        runs with):

        ORAONE_BACKUP_DIR=/var/backups/oraone
        ORAONE_BACKUP_PASSPHRASE_FILE=/root/oraone-backup-passphrase
        DB_HOST=<FILL: database host - usually postgres>
        DB_PORT=5432
        DB_NAME=oraone
        DB_USER=<FILL: database user>
        DB_PASSWORD=<FILL: database password - secret>

Step 5. Run the backup once by hand and check that a file appears in /var/backups/oraone.
Step 6. Schedule it weekly with cron, as root. This changes the server, so approve it first.
        Reply with the day and time you want.
Step 7. Set up the off-host copy after each backup, using a tool you choose (for example rclone).
        This needs your destination account, so I cannot do it for you.
Step 8. Restore drill. Do this on a separate machine or a disposable database, NEVER on production:
            cd backend
            python scripts/backup_restore_drill.py --help
        Follow the script's instructions. Record the date, the backup file used, and whether row counts
        and schema matched, in docs/operations/BACKUP-RESTORE.md under "Drill evidence".

Tell me: "backup once done", "off-host copy done", and "restore drill passed on <date>".
