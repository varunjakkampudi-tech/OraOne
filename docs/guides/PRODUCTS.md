# OraOne products: a guide for operators and end users

This guide explains each part of OraOne in plain language. For each part it says what it
does, what you need before you start, how to set it up, what it does not do yet, and
which automated tests cover it.

Setting names are written in code (for example `TWILIO_ACCOUNT_SID`). Use them to find
the setting in [CONFIGURATION](../operations/CONFIGURATION.md). Never type a real value
into this guide, into a ticket or into a chat.

## How to read the status line

Every section starts with a **Status in this code** line. The statuses are:

- **Available**: the feature works in the code for the scope described. You still need
  the accounts and settings it lists, and it has not been verified against live providers.
- **Partly available**: some of the feature works. A step is missing, and the section says which.
- **Blocked by a setup gap**: the code is written, but there is no way to finish the set-up
  through Studio or the API. Ask the engineering team before you promise it to a customer.
- **Not built**: no code in this repository.

These statuses describe the code at commit `e6f8237` on branch `feat/product1-launch`, with a
clean working tree when this guide was written. Committed code is not the same as a live
service. Nothing here is a launch date or a claim that the product is live for customers.
Production readiness is tracked in [PRODUCT-PORTFOLIO](../PRODUCT-PORTFOLIO.md), which uses the
three portfolio labels: **Built**, **Live-needs-account** and **Planned**. The mapping is:
Available = Built; Partly available = Built (partial); Blocked by a setup gap = Live-needs-account
(the account is needed, and the setup step is not yet in Studio); Not built = Planned.

Two words are used throughout:

- **Workspace**: the space where one business keeps its assistants, leads and settings.
- **Assistant**: the AI helper a workspace configures. The code calls it an _agent_.

## 1. Website chat widget

**Status in this code: Available.**

### What it does

Visitors to your website can chat with an assistant. The assistant answers from the
documents and web pages you add to it. Visitors can leave their contact details, and the
assistant can ask for a person. Each conversation appears in the Inbox and in Leads.

If the AI model is unavailable, the assistant does not invent an answer. It shows the most
relevant passages from your documents and says that they were not generated by the model.

### What you need first

- A workspace, and an assistant with its instructions (system prompt) saved. An assistant
  without instructions cannot be activated.
- Knowledge: documents or website pages added under Knowledge.
- A website you can edit, where you can paste one line of code.
- The domain of that website, so the chat is allowed to load there.
- On the server: `OPENROUTER_API_KEY`, so answers are generated. Also `FRONTEND_URL`, and
  `WIDGET_CDN_BASE` or `WIDGET_API_BASE` if the widget is served from a different address.

### How to set it up

1. Open the assistant in AI Studio, then **Add to website**, then **Create chat widget**.
2. Under **Allowed websites**, enter each domain on its own line, for example `example.com`.
   In production, an empty list blocks every site.
3. Copy the code. There are four ways to install it:
   - a script tag on any page (`widget.js`, with `data-widget-id`);
   - the browser SDK, which exposes `window.OraOne` for opening, closing and sending messages;
   - a React or Next.js component;
   - the REST API, with an API key that has the `chat:write` scope, for your own server.
4. Paste the code on the site, then choose **Publish widget**. Pausing the widget hides it.

Publishing also makes an assistant that is ready (it has instructions) active.

The full installation guide, with the attributes and SDK methods, is in
[WEBSITE-WIDGET](WEBSITE-WIDGET.md).

### What it does not do yet

- Visitors cannot sign in. Each visitor gets a random identifier in their browser.
- The widget sends and shows plain text. This review did not confirm that staff replies
  typed in the Inbox appear live inside the widget. Test this before you promise live hand-over.
- Local development uses a memory store, so rate limits and sign-in codes are shared only
  within one process. Production needs Redis.

### How it is tested

Backend: `test_product_widgets.py`, `test_product_widget_security.py`,
`test_widget_domain_policy.py`, `test_widget_knowledge_bindings.py`,
`test_cors_rate_limit.py`, `test_assistant_fallback_honesty.py`,
`test_generated_flag_paths.py`. Frontend: `src/lib/studio-os.test.ts` covers the Studio channel
status rules, which include the website chat page.

## 2. AI Voice agent

**Status in this code: Blocked by a setup gap.** The call handling is written, but no
screen and no API can create the voice binding that connects a phone number to an
assistant.

### What it does

When someone calls your business number, the assistant answers. It listens for each turn,
answers from the same knowledge as the website chat, and speaks the reply. When the caller
asks for a person, the call is transferred to the team number if one is set. If no team
number is set, the caller hears that no line is available and the call ends.

Spoken replies use ElevenLabs when both `ELEVENLABS_API_KEY` and `ELEVENLABS_VOICE_ID` are
set. Otherwise, or after any failure in a turn, Twilio's built-in voice is used. The same
voice path is used by outbound calls (see [Calls](#11-calls)).

### What you need first

- A Twilio account, with a voice-capable phone number. Settings: `TWILIO_ACCOUNT_SID`,
  `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`.
- `PUBLIC_API_BASE_URL`, set to your public `https://` address. Twilio signs this exact address.
- Optional: `VOICE_HANDOFF_NUMBER` (an E.164 number for transfers), `VOICE_SAY_VOICE`
  (default `alice`), `ELEVENLABS_API_KEY`, `ELEVENLABS_VOICE_ID`, `ELEVENLABS_MODEL_ID`.
- A Redis service in production (`REDIS_URL`), because spoken audio is cached there when
  there is more than one worker.

### How to set it up

1. Set the Twilio and public-address settings on the server. Recreate the containers.
2. Create the assistant and add its knowledge.
3. Create the **voice binding** that links the phone number to the assistant. The binding
   is a database record, with channel `voice`, the number in E.164 form, `enabled` set to
   true, and the assistant's identifier. **No screen or API in this repository creates it.**
   The Studio channel page for AI Voice shows "Not connected yet" until it exists.
4. In Twilio, point the voice webhook of the number at `/api/voice/inbound` (HTTP POST).
5. Call the number and check the reply.

### What it does not do yet

- There is no set-up screen or API for the voice binding (see step 3). Without it, callers
  hear that the number is not available.
- Speech is handled turn by turn with Twilio's speech input. This is not a streaming voice model.
- The voice code does not record call audio. Each spoken turn is saved as a message in the
  conversation, so the Inbox shows what was said.
- No live call was placed in this review.

### How it is tested

`test_voice_agent.py` (TwiML builders, webhook signatures, speech turns, hand-over and the
outbound greeting), `test_voice_tts.py` (ElevenLabs selection, Twilio fallback, audio route,
cache and log hygiene), `test_twilio_signature.py`, `test_product_contact_policy.py` (the voice
conversation channel).

## 3. WhatsApp

**Status in this code: Blocked by a setup gap.** Inbound and reply code is written for two
routes, Twilio and the Meta WhatsApp Cloud API. The binding that links a number to an
assistant can only be created in the database.

### What it does

Customers message your WhatsApp Business number. The assistant answers in the same
conversation memory as the website chat, so a customer who started on the website keeps
their context. The conversation appears in the Inbox.

### What you need first

Choose one route.

- **Through Twilio**: a Twilio account with a WhatsApp sender. Settings: `TWILIO_ACCOUNT_SID`,
  `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`, `PUBLIC_API_BASE_URL`.
- **Through Meta**: a Meta Business account with WhatsApp Business, a business phone number
  that no other WhatsApp account uses, and a verified business name in Meta Business Manager.
  Settings: `META_WHATSAPP_ACCESS_TOKEN`, `META_WHATSAPP_APP_SECRET`,
  `META_WHATSAPP_VERIFY_TOKEN`. The binding needs the `phone_number_id` of that number.

Meta's and Twilio's own verification of the business and the sender is outside this
repository. Check their current requirements.

### How to set it up

1. Set the server settings above. Recreate the containers.
2. For Meta, in the Meta app's WhatsApp settings, set the callback URL to
   `<your public address>/api/channels/meta/inbound` and the verify token to
   `META_WHATSAPP_VERIFY_TOKEN`. Subscribe to the messages field.
   For Twilio, set the incoming-message webhook of the sender to
   `<your public address>/api/channels/twilio/inbound`.
3. Create the WhatsApp binding (a database record, channel `whatsapp`). Engineering must do
   this step until a screen or API exists.
4. Send a test message from a phone.

### What it does not do yet

- No screen or API creates the WhatsApp binding.
- This review found no support for approved message templates. Messages that a provider
  refuses are logged with the HTTP status, and no reply is sent.
- Outbound messages from workflows and marketing use the same path, so the same limits apply.

### How it is tested

`test_meta_whatsapp.py` (parsing, signature, handshake and reply path),
`test_product_whatsapp.py` (signed webhook flow, binding, reply delivery and refused handshakes),
`test_product_twilio.py` (SMS and WhatsApp through Twilio), `test_product_webhook_auth.py`.

## 4. Instagram

**Status in this code: Blocked by a setup gap.** The code handles direct messages. The
binding that links an Instagram account to an assistant can only be created in the database.

### What it does

Replies to direct messages sent to your Instagram professional account, in the same inbox
as your other channels. The code handles direct messages only. It does not handle comments
or stories.

### What you need first

- An Instagram professional account (Business or Creator), linked to a Facebook Page.
- Access to that Page in Meta Business Manager.
- A Meta app with Instagram messaging. Settings: `META_INSTAGRAM_ACCESS_TOKEN` (the page or
  Instagram-scoped token), and `META_WHATSAPP_APP_SECRET` and `META_WHATSAPP_VERIFY_TOKEN`,
  which the Instagram webhook shares with WhatsApp.

Meta's app review for the messaging permissions is outside this repository.

### How to set it up

1. Set the server settings above. Recreate the containers.
2. Set the callback URL to `<your public address>/api/channels/meta_instagram/inbound` and the
   verify token to `META_WHATSAPP_VERIFY_TOKEN`.
3. Create the Instagram binding (database record, channel `instagram`), with the
   `instagram_account_id` of the account. Engineering must do this step.
4. Send a direct message to the account and check the reply.

### What it does not do yet

- No screen or API creates the binding.
- Comments and stories are not handled.
- Replies are sent only when the Instagram token is set. Otherwise the message is stored
  without a reply being sent.

### How it is tested

`test_meta_instagram.py` (parsing, signature, handshake and reply path),
`test_product_instagram.py` (signed webhook flow, account binding and replies).

## 5. Omnichannel inbox

**Status in this code: Partly available.** The inbox lists conversations from every channel
and keeps one memory per customer. Replies typed by staff are stored only in OraOne.

### What it does

- Lists conversations from the website chat and from every connected channel (WhatsApp,
  SMS, Instagram, email, Telegram and the mobile SDK), with the customer's name, contact
  details and the thread.
- Recognises a returning customer by phone number, email or handle. The assistant then has
  the same memory across channels.
- Stops AI replies to a contact who sends `STOP`, and records that contact as opted out.
- Ignores a provider's repeated delivery of the same message, so the customer gets one answer.
- Lets staff add a message to a conversation.

### What you need first

- At least one channel connected (see the channel sections above), or use the website chat.
- Staff accounts in the workspace, with the right roles (see the team page in Studio).

### How to set it up

Open **Inbox** in Studio. Select a conversation to read it and reply. Nothing else is needed,
once the channels that feed it are working.

### What it does not do yet

- **Staff replies are not sent to customers on WhatsApp, Instagram, SMS or email.** They are
  saved in OraOne only. Staff who need to reply on those channels must use the channel's own app.
- **Email replies are not delivered by the application.** The email channel stores the
  answer, and a separate process must send it.
- Studio labels the Omnichannel inbox as "planned" in its overview. The inbox page exists
  and works for the conversations it holds.

### How it is tested

`test_product_webhook_auth.py` (channel webhooks, Telegram path token, de-duplication, log
hygiene), `test_product_tenant_security.py`, `test_phase5_org_isolation.py` (tenant isolation),
`test_product_contact_policy.py` (STOP replies). Frontend: `src/test/live-api.test.ts`.

## 6. AI Studio and Agent Builder

**Status in this code: Available** for assistants. The wider Product 6 scope in
[PRODUCT-PORTFOLIO](../PRODUCT-PORTFOLIO.md) is not built.

### What it does

You create an assistant and shape how it answers:

- its name and instructions (system prompt), which must not be empty before it can be activated;
- its model. Some models need a higher plan (see below), and the default comes from `OPENROUTER_MODEL`;
- temperature and the length of replies (capped by `AI_MAX_OUTPUT_TOKENS`);
- the knowledge it can use (knowledge bindings);
- versions: publish a snapshot, compare two versions, and roll back;
- a playground to try questions before you publish;
- analytics for conversations and answers;
- installation on a website, or on a channel that is set up.

An assistant has one of four states: draft, active, paused or archived. An active assistant
answers. A paused one does not.

Helpers for operators are also available, for example a meeting summary, a conversation
quality review, a forecast, an outreach draft, an experiment summary and a general copilot.
They always return a result. When the model is unavailable, the result says that it is a fallback.

### What you need first

- An OpenRouter account, with its key stored as `OPENROUTER_API_KEY`.
- Knowledge added to the workspace.
- A plan that allows the model you choose. Models in the catalogue need these plans:
  - `openai/gpt-5.5` and `anthropic/claude-sonnet-4`: Business;
  - `google/gemini-2.5-pro`: Starter;
  - `google/gemini-2.5-flash`: every plan.

### How to set it up

1. Open **AI Studio**, then **New assistant**. Give it a name and write its instructions.
2. Attach knowledge in the knowledge tab.
3. Try questions in the playground.
4. Publish a version, then activate the assistant.
5. Install it on a website (see [Website chat widget](#1-website-chat-widget)).

### What it does not do yet

- There is no visual flow builder in this repository.
- An assistant cannot call custom external tools defined by the customer. No such feature was
  found in the code review.
- A platform-wide model choice (`AI_FORCE_MODEL`) overrides the plan and the model of every assistant.
  Operators use it for cost control only.

### How it is tested

`test_phase6_agents_crud.py`, `test_agent_knowledge_bindings.py`, `test_agent_analytics.py`,
`test_rag_model_pin.py` (the model boundary for every reply), `test_assistant_fallback_honesty.py`,
`test_generated_flag_paths.py`, `test_model_catalogue.py`, `test_ai_provider_fallback.py`,
`test_openrouter_embeddings.py`, `test_phase6_knowledge.py`, `test_phase7_processing.py`
(document processing and chunking).

## 7. Marketing

**Status in this code: Partly available.** Public contact and newsletter forms work. The
campaign engine is written, but no email sender is connected, and the SMS and WhatsApp
sends need bindings that cannot yet be created.

### What it does

- **Contact and newsletter endpoints** (`/api/contact` and `/api/newsletter`) store a submission
  and a sign-up. This review found the endpoints, but did not find the public contact page
  calling them. Check that page before you rely on it.
- **Consent and do-not-contact rules** apply to outbound calls, workflow messages and campaigns.
  The rules are:
  - consent must be given before a lead is contacted. Campaigns never use the reply exception,
    which applies only to replies to a message the contact sent;
  - a do-not-contact list, managed through `/api/contact-policy/do-not-contact`;
  - an opt-out from a `STOP` reply;
  - quiet hours, from 21:00 to 08:00 in the contact's local time;
  - at most two outbound attempts to one contact in 24 hours.
- **Campaigns** (API under `/api/marketing`). A campaign has a channel (email, SMS or WhatsApp),
  a message, and up to 500 leads. The plan step checks each lead against the rules above and
  records a plain reason for every skipped lead. The send step sends in batches of 25. A
  campaign can be cancelled while it is a draft. Email messages carry a signed unsubscribe link,
  valid for 90 days.

### What you need first

- For the contact forms: nothing beyond the public site.
- For campaigns: leads with consent recorded, and a channel that can send (see below).
- Staff with the leads permission (campaign creation and sending need it).

### How to set it up

Campaigns are created and sent through the API. The Studio page for Marketing exists
(`/studio/marketing`), but this review did not confirm all of its screens end to end.

- **Email**: no email delivery is connected. Sends fail with the reason
  "Email delivery is not connected on this server yet." Do not promise email campaigns.
- **SMS and WhatsApp**: the sender needs an enabled binding for the channel. The binding is a
  database record (see the WhatsApp section). Without it, the send fails with a plain reason.
- **Unsubscribe links** use `PUBLIC_API_BASE_URL`, and are signed with the JWT secret.

### What it does not do yet

- No email delivery. No scheduled sending (the campaign status for it exists, but no API
  schedules a campaign). No segments or audience builder beyond selecting leads.
- A send runs inside the request that starts it, so a large campaign can take a long time to
  return. Keep campaigns small until this is changed.
- A message that a provider refuses is recorded as not sent for that recipient.

### How it is tested

Backend: `test_marketing_campaigns.py` (consent planning, honest sending, the double-send guard,
roles, isolation and unsubscribe), `test_product_contact_policy.py`, `test_product_outreach.py`,
`test_product_outreach_timing.py`, `test_outreach_policy.py`, `test_email_log_privacy.py`.
Frontend: `studio-marketing.test.tsx`.

## 8. Marketplace

**Status in this code: Available** for the catalogue as it is. The catalogue is part of the
code, not a list that customers can publish to.

### What it does

Install a ready-made item into your workspace:

- **Agent templates** (eight): dental clinic, real estate, restaurant, e-commerce support,
  SaaS onboarding, education admissions, insurance and automobile. Installing one creates a
  real assistant, with its instructions, that you can edit.
- **Integration blueprints** (two): Google Calendar and HubSpot. An installation works only
  after you connect that provider in Integrations. Both providers have a connection flow now,
  but each needs its OAuth settings on the server (see Integrations).
- **Workflow recipe** (one): the Lead Follow-up Sequence. Installing it creates a **draft**
  workflow. It never starts active. It is installed only when every step it uses is supported.

Installing the same item twice returns the existing installation. Reviews of listings are
supported by the API.

### What you need first

- A role that can create assistants (`agents.write`).
- For the integration blueprints: the provider connected first (see Integrations).

### How to set it up

1. Open **Marketplace** in Studio and choose an item.
2. Read what it sets up, then choose **Install** and confirm.
3. For an assistant: review its instructions, add knowledge, test it, then activate it.
4. For a workflow: open the draft, check each step, then turn it on.

### What it does not do yet

- Customers cannot publish their own listings. The catalogue is maintained in code.
- Listings cannot be edited from Studio.
- The Studio overview labels the Marketplace "planned", although the page works.

### How it is tested

`test_product_marketplace.py` (listing lookup, install idempotency, uninstall and review
ownership), `test_marketplace_install_gating.py` (installs gated on real capability, with no

## 9. Integrations

**Status in this code: Partly available.** Six providers can be connected through OAuth.
Only Google Drive syncs data today. Outbound webhooks work.

### What it does

- **Connect** a provider with OAuth. The provider's consent screen opens, you approve, and
  the connection is stored with its tokens encrypted.
- **Google Drive** syncs the folders or files you choose into the knowledge base, read-only.
- **Outbound webhooks** (Studio, **Webhooks**): send events from OraOne to a URL you control.
  Each endpoint has a signing secret, which you can rotate. You can send a test event. Private
  and internal addresses are refused, to prevent server-side request forgery.

| Provider                             | Connect (OAuth)                                        | Data sync       |
| ------------------------------------ | ------------------------------------------------------ | --------------- |
| Google Drive                         | Yes                                                    | Yes (read-only) |
| Google Calendar                      | Yes                                                    | Not yet         |
| Google Sheets                        | Yes                                                    | Not yet         |
| Slack                                | Yes                                                    | Not yet         |
| Notion                               | Yes                                                    | Not yet         |
| HubSpot                              | Yes                                                    | Not yet         |
| Gmail, Salesforce                    | Not connectable (listed only)                          | No              |
| Zapier, Make, signed generic webhook | Not available (inbound triggers are not available yet) | No              |

### What you need first

- For each provider you use, an OAuth client registered with that provider, with its client
  identifier and secret stored on the server (see the OAuth settings in
  [CONFIGURATION](../operations/CONFIGURATION.md), sections 9 and 13).
- The redirect URI in each provider's console must match the server setting exactly. Google
  Drive uses `/api/integrations/google/callback`. The other providers use
  `/api/integrations/oauth/callback`.
- For webhooks: an HTTPS endpoint you control.

### How to set it up

1. In Studio, open **Integrations**, choose the provider and select **Connect**. If it
   answers "Not configured yet", the server is missing the OAuth settings. Ask the
   administrator to add them and recreate the containers.
2. Approve access at the provider. You are returned to Studio.
3. For Google Drive: choose **Browse**, select the folders, then **Sync**.
4. For a webhook: **Webhooks**, add the endpoint, choose the events, send a test, and store the
   signing secret in your own system.

### What it does not do yet

- Only Google Drive syncs data. The other providers can be connected but move no data.
- Connectors for Zapier, Make and inbound triggers are not available.
- The integration trigger type exists in the workflow model, but no code fires it.

### How it is tested

`test_product_integrations.py`, `test_integrations_expansion.py` (new provider status, fail-closed
OAuth, signed outbound events), `test_integrations_setup_status.py`,
`test_integration_connection_mode.py`, `test_oauth_state.py` (state binding and replay protection),
`test_connector_no_demo_data.py`, `test_knowledge_source_security.py`, `test_webhook_security.py`
(webhook SSRF and redirect safety), `test_webhook_outbox.py`, `test_webhook_rate_limit_tiers.py`.
Frontend: `src/test/integrations-api.test.ts`, `src/lib/integration-status.test.ts`.

## 10. Workflow automation

**Status in this code: Available** for the triggers and steps listed below, with the
send-message limits described.

### What it does

A workflow is a list of steps that run in order. Each step reads the variables set by the
steps before it.

**Triggers**

- **Manual**: you run it on demand, or through the API.
- **Schedule**: an interval in minutes, or a preset of daily, hourly or weekly.
- **Event**: `lead.created` (a lead is created) or `message.received` (a customer message arrives).

**Steps**

- AI steps: write a prompt, classify text, extract fields, summarise, judge sentiment, translate.
- Knowledge search, and running one of your assistants.
- Condition (stop the run unless a rule holds), transform (build a text value from a template).
- Delay (waits durably, and resumes on the scheduler, not by sleeping).
- Approval (pauses for a person to approve or reject, in Studio or through the API).
- Send message on the lead's channel. It checks consent and needs an enabled channel binding.
- Create task. This is stored as a record linked to the lead.
- Webhook (an HTTP POST to a URL you choose; only `http` and `https`).
- Notification. This is recorded in the run; it is not sent by email or Slack.

Each step can retry, and can continue after an error. Workflows keep versions, and you can
roll back to an earlier one.

### What you need first

- A workflow, with at least one step.
- For AI steps: `OPENROUTER_API_KEY`.
- For a send-message step: an enabled channel binding (see the channel sections) and consent
  on the lead. Email delivery is not connected.
- For a webhook step: an HTTPS endpoint.

### How to set it up

1. In Studio, open **Workflows**, then **New workflow**. It starts as a draft.
2. Add the steps and set their settings.
3. Run it once manually, and read the run's steps.
4. Choose the trigger and turn the workflow on.

Workflows that use an unknown event name are refused when saved.

### What it does not do yet

- The integration trigger type exists, but nothing fires it.
- A notification step records only. It does not send email, Slack or SMS.
- Send-message steps fail for WhatsApp, SMS and Instagram until the binding exists, and for email
  until email delivery is connected.
- A draft workflow never runs. A marketplace install of a workflow always starts as a draft.

### How it is tested

`test_product_workflows.py` (approval, event triggers, the schedule loop and API guards),
`test_workflow_engine_completion.py` (triggers, durable waits, the send and create-task steps),
`test_product_workflow_senders.py` (channel bindings, provider readiness and consent),
`test_webhook_security.py`. Frontend: `src/components/oraone/studio-workflows.test.tsx`.

## 11. Calls

**Status in this code: Blocked by a setup gap.** The campaign engine, its consent rules and
its Twilio integration are written. A campaign also needs an AI Voice binding for the calling
number, and that binding cannot yet be created through Studio or the API. Without it, the
person answering hears that the number is not available. Studio labels Calls as "planned".

### What it does

A call campaign calls a list of leads, one call at a time, through Twilio.

1. Choose the leads, either by selecting them or by their status and temperature.
2. Give the campaign a name and a timezone (an IANA name, such as `Europe/London`).
3. Each lead is checked against the outreach rules. Leads that fail a rule are skipped, and
   the skip reason is recorded: no consent, a do-not-contact entry, an opt-out, quiet hours,
   the daily limit, an invalid number, or no timezone for the lead.
4. **Start** places the first call. When a call ends, Twilio reports it to OraOne, and the next
   call is placed. **Pause** stops new calls, and lets a call already in progress finish.
5. The attempt list shows each attempt, its outcome and its reason.

Every outbound call is subject to the same consent rules as marketing (see
[Marketing](#7-marketing)).

### What you need first

- Twilio settings: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`, and
  `PUBLIC_API_BASE_URL` set to an `https://` address. Without them, starting a campaign returns
  an error that names the missing settings.
- An AI Voice binding for the calling number (see [AI Voice agent](#2-ai-voice-agent)).
- Leads with an E.164 phone number, and consent recorded on each lead. Imported consent is
  recorded as the value in the file, and is marked "confirm the source".
- A role with calls permission (`calls.write`).

### How to set it up

1. Set the Twilio and public-address settings. Recreate the containers.
2. Create the AI Voice binding (engineering step, until a screen exists).
3. Import leads with a consent column (see [Leads and import](#12-leads-and-import)).
4. In Studio, open **Calls**, create a campaign, choose the leads and the timezone.
5. Choose **Start**. Watch the attempts. Pause if needed.

### What it does not do yet

- No set-up screen or API creates the AI Voice binding that outbound calls need.
- The campaign advances only when Twilio reports a call's end, or when someone presses Start
  again. There is no timer. A call still marked as in progress after 30 minutes is checked with
  Twilio the next time the queue moves.
- No call recording, transcripts, or scheduled call windows beyond the quiet-hours rule.
- Studio labels Calls as "planned" in its overview, although the page works.

### How it is tested

`test_product_calls.py` (campaign lifecycle, dial-time policy, Twilio status transitions and
route guards), `test_outbound_calls.py` (planning rules, one call at a time, Twilio REST and
callbacks), `test_twilio_signature.py`, `test_product_outreach_timing.py` (quiet hours, timezone
fallback, live calls). No frontend test specific to calls was found in this review.

## 12. Leads and import

**Status in this code: Available.**

### What it does

- **Leads** come from the website chat (when a visitor leaves their details), from
  conversations, from manual entry, and from imports. Each lead has a name, email, phone,
  company and notes, and a status: new, contacted, qualified, won or lost.
- **Score and temperature.** Each lead gets a score from 0 to 100, from how complete its
  contact details are and from buying-intent words in its messages. The temperature is hot,
  warm or cold. The score is deterministic, so the same lead always gets the same score.
- **Statistics** (pipeline KPIs) and the chat thread that produced each lead.
- **Import** of a CSV or XLSX file. The file must be at most 5 MB, with at most 5,000 data rows.
  Each file is checked before it is read, including its file type, its structure and whether
  it contains macros (macro-enabled files are refused).

### Import, step by step

1. In Studio, open **Leads**, then **Import**, and choose the file.
2. Read the preview. It counts the rows that are valid, the duplicates and the invalid rows.
   Nothing is saved yet.
3. Choose **Save valid rows**. Only valid rows are saved, and they are tagged as imported.

The columns are recognised by name. For example, `name`, `phone`, `mobile`, `email`,
`company`, `notes`, and `consent` (or `marketingconsent`, `optin`, `consentstatus`).

- A duplicate is a lead that already exists in the workspace, or a row repeated in the file.
  Duplicates are skipped.
- The consent column accepts yes, no or blank. Yes is recorded as granted. No is recorded as
  denied. Blank is unknown. Any other value makes the row invalid.
- Imported consent is what the file says. OraOne did not capture it, so it is recorded with
  the note "Imported consent, confirm the source". Only confirm consent that you have.

### What it does not do yet

- No enrichment of contact details from outside sources.
- Consent provenance can be read on leads, but cannot be written through the API.

### How it is tested

`test_lead_import.py` (CSV and XLSX parsing, validation, duplicates and saving),
`test_lead_consent_read.py` (consent provenance is visible on reads and cannot be written
through the API), `test_product_outreach_timing.py` (import consent in the outreach rules),
`test_product_tenant_security.py` (lead and calls permissions). Frontend:
`src/test/lead-consent.test.ts`.

## 13. OraOne OS hub

**Status in this code: Built** for the hub and its status rules. OraOne OS is the name of the
signed-in home page (`/studio`). It is not a separate product. The long-term vision is in
[PRODUCT-PORTFOLIO](../PRODUCT-PORTFOLIO.md), row 10.

### What it does

The hub lists ten areas. Each shows its status and one primary action:

| Area              | Status shown                                                  | Action                               |
| ----------------- | ------------------------------------------------------------- | ------------------------------------ |
| Website chat      | From the channel rows: Connected, Paused or Not connected yet | Set up or Open (channel setup page)  |
| AI Voice          | As above                                                      | Set up or Open                       |
| WhatsApp          | As above                                                      | Set up or Open                       |
| Instagram         | As above                                                      | Set up or Open                       |
| Omnichannel inbox | Planned (roadmap label)                                       | Open (inbox)                         |
| AI Studio         | Available (roadmap label)                                     | Open (assistants)                    |
| Marketing         | Not connected yet                                             | Set up, with no screen behind it yet |

| Integrations      | Not connected yet                                             | Open (integrations)                  |
| Calls             | Planned (roadmap label)                                       | Open (calls)                         |

Channel areas read the channel rows for the workspace's first assistant. If that request is still
loading, the card says "Checking…". If it fails, the card says "Not connected yet". Nothing is shown

The channel setup pages (`/studio/channels/...`) list the accounts and settings each channel needs,

### What you need first

2. Choose an area. For a channel, choose **Set up** and follow the checklist on its page.
3. Choose **Open** on an area that is already connected.

### What it does not do yet

- A channel shows as connected only when its row is enabled and active. The rows for WhatsApp,
  Instagram and AI Voice cannot yet be created from Studio (see those sections). So those cards
  cannot reach Connected through the normal flow.
- The Marketing card has no screen behind it.
- The roadmap labels for the Omnichannel inbox, Marketplace and Calls read "Planned". Those screens
  work for the data they hold, so the label is out of date.

## 14. Admin console

**Status in this code: Partly available.** The configuration console is live for platform
super-admins. The other administration pages show empty states until the services they need are
connected. Nothing on those pages is simulated.

### What it does

The admin area sits under `/admin` and is for platform staff only.

- **Configuration** (`/admin/config`) is live. It lists every key in the configuration registry by
  group, for the `local` or `production` view. It shows secrets only as "Set, ends in XXXX" or
  "Not set". A change is first saved as a **draft**, with the key name typed to confirm and a
  reason of 10 to 500 characters. A super-admin then **publishes** the reviewed drafts. Publishing
  takes effect only after the API restarts. Keys the console cannot manage are shown read-only.
  The API is under `/api/admin/config`.
- **Secret inventory** (`GET /api/super-admin/secrets`) returns, for twelve names, whether each is
  set and a masked tail. It is an API only. No screen calls it, and it is read-only.
- **Other pages** (users, organizations, subscriptions, billing, usage, error logs, audit logs,
  support, monitoring, infrastructure, AI models, security, products, entitlements, feature flags
  and settings) show a table definition and an empty state. For example, "Error events are
  unavailable until authorized observability services are connected." The backend has matching
  super-admin endpoints (for example `/api/super-admin/audit-logs` and `/api/super-admin/feature-flags`),
  but the admin screens do not call them.

### Logs, analytics and beta

- **Logs.** There is no log view or log download in the admin area. Error logs and audit logs are
  empty states. Engineering work on admin logs is listed in [blocker.txt](../../blocker.txt).
- **Analytics.** The global usage and monitoring pages are empty states. The screens do not show
  metered or measured figures.
- **Beta.** A product can have the `beta` status in the product model, and the entitlement key
  `beta_features` marks the opt-in beta surface. The feature-flag screen is a placeholder. The
  backend's `PATCH /api/super-admin/feature-flags/{key}` is not called by any screen. Beta testers
  are not yet added through the console (see `blocker.txt` item 10).

### What you need first

- A platform account with the `super_admin` role. The first one is granted by an engineer on the
  server (see `blocker.txt` item 8). The `admin` platform role does not get access to these routes.
- For saved values: `INTEGRATIONS_ENCRYPTION_KEY` set on the server. Saved values are encrypted with
  it. Changing it makes stored values unreadable.

### How to set it up

1. Sign in with the super-admin account.
2. Open **Configuration** and choose the environment tab (`Local` or `Production`).
3. To change a console-managed key, open its row, enter the new value (no line breaks, at most 2048
   characters), type the key name in **confirm**, enter a reason and choose **Save draft**. Do not put
   secrets in the reason.
4. Open **Drafts**, check the diff, type the environment name in **confirm**, enter a reason and
   publish. If a draft changed after you reviewed it, the publish is refused.
5. Restart the API so that every worker loads the published values, for example
   `docker compose --env-file .env.production -f docker-compose.prod.yml restart backend workers`.
   **Reload** re-reads the saved values into one process only (it needs the confirm text `RELOAD`),
   so it is not a substitute for a restart. The page shows **Restart required** when a saved change
   is newer than the running process.
6. Check the masked values. Secrets must show only "Set, ends in XXXX" or "Not set".

The full rules, including the audit records, history and key rotation, are in
[ADMIN-CONFIG](ADMIN-CONFIG.md).

### What it does not do yet

- No log viewer, no log download, no audit-log screen, no analytics screen.
- No feature-flag or beta-tester screen. No screen for the entitlements overview.
- This section describes commit `e6f8237`. Uncommitted work in the working tree at the time of
  writing adds admin log, analytics, feature-flag and beta screens and new migrations. It is not
  counted here. Update this section when that work is committed and tested.
- No single sign-on for administrators. Sign-in is by email code, like every other account.
- Other admin pages cannot show data until their services are connected.

### How it is tested

Backend: `backend/tests/test_admin_config_console.py`, `backend/tests/test_platform_rbac.py`,
`backend/tests/test_authorization.py`, `backend/tests/test_security_authz_hardening.py`.
Frontend: `src/lib/admin-config.test.ts`. End-to-end: `e2e/admin.spec.ts`.
